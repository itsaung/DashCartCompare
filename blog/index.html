Checkpoint 2 review, round two: a fake review record, a regex backtracking bug, and a dimension heuristic that took three tries

2026-09-16 · code reviewbug fixestesting

A second review pass on Checkpoint 2 found three more issues: the manual review record's every row defaulted to "OK" whether or not anyone had checked it, and re-running the script would have erased any real decision anyway; a specific bare-oz parsing choice (documented as deliberate) turned out to have a real consequence for beverages that wasn't being surfaced anywhere; and four more shopping-list inputs had validation gaps, including a genuine regex backtracking bug. All fixed. Full detail in dash/PARSING_AUDIT.md.

The manual review record wasn't actually reviewing anything

The first version of manual_review.py sampled 100 products and wrote them to MANUAL_REVIEW.md with every row's status defaulted to "OK" and a discrepancies section reading "None" — regardless of whether a human (or anything else) had actually looked at any of them. Re-running the script would have silently regenerated the whole file, erasing a real discrepancy note if one had ever been written by hand. The deeper problem: even a genuine visual check only compares the catalog's own raw_title/raw_size against themselves — it can't catch the scraper having copied something wrong from the source in the first place, because there's no independent source in the loop at all.

Redesigned around three rules: generation only ever creates rows in an explicit "unreviewed" state; review decisions live in a separate file (manual_review_decisions.json) that re-running generation preserves rather than overwrites; and every row carries a source_url — the live DoorDash product page — so a "verified" decision means something was actually checked against an independent source. To prove the mechanism works rather than leave it as untested infrastructure: 7 of the 100 rows (one per store, three from ALDI) were checked against a fresh, independent re-fetch of their live category page — not a re-read of the stored CSV. Title and price matched exactly in all 7. The other 93 are honestly "unreviewed", not quietly treated as fine.

Bare "oz" on beverages: a documented rule with an unflagged consequence

The review sample surfaced three products — Ripple plant milk, Modelo beer cans, a FocusAid energy drink — all recorded with bare "oz" and therefore parsed as weight, per the rule documented in the first Checkpoint 2 entry. That rule itself wasn't wrong, but a flexible-mode basket request in fluid ounces would never match these, purely from a dimension mismatch unrelated to whether the product fits the request. The fix is a review flag, not a silent reinterpretation to volume — that would just be a different silent guess, arguably a worse one since it would look more "resolved" than it actually is.

Getting the heuristic right (added to build_normalized_catalog.py, which sees the product title/category that the size-string-only normalize.py deliberately doesn't) took three checked iterations:

Four more shopping-list validation gaps

The "12% milk" case is the sharpest: an earlier fix added a (?!%) lookahead so "2%" wouldn't be torn into a number and a stray percent sign. But a lookahead placed right after a greedy \d+ doesn't stop backtracking — for "12%", the engine just tries the shorter match "1", for which "not followed by %" is true (the next character is "2", not "%"), and the lookahead happily succeeds on the wrong match. Fixed by removing the lookahead and checking, after the full greedy match, whether the actual next character is "%" — against the real matched text, not hoping backtracking won't route around a lookahead.

Checkpoint 2 review: confidently-wrong parses, a snapshot bug, and a missing dataset artifact

2026-09-16 · code reviewbug fixestesting

An external review of the Checkpoint 2 work (normalization + parsing, previous entry) found four real issues: a snapshot-selection bug inflating DashMart's product count, five shopping-list inputs that parsed to a wrong answer with no review flag, three crash inputs and a missing-validation gap in the package-size parser, and a missing dataset artifact — the plan asks for one reproducible normalized table, and this checkpoint had only produced the parsing functions, not that table. All four are fixed. Full detail is in the updated dash/PARSING_AUDIT.md; this entry summarizes what was wrong and what changed.

DashMart's product count was inflated by mixing two scrape runs

doordash_store_1042759_items.csv is a single file two different scrape runs (Sept 8 and Sept 16) had appended to. coverage_report.py deduped it by keeping the last row seen per item_id across the whole file — which means a product present only in the older run still counted as "current" simply because no later row overwrote it. Checked directly: the true latest run has 3,022 products; the keep-last dedupe produced 3,326 — 304 products that should not have been counted as current inventory. Fixed by filtering to the single most recent scraped_at value only (latest_snapshot_only()), used consistently now by the coverage report, the corpus test, and the new normalized catalog builder.

Five shopping-list inputs parsed to a wrong answer, not a rejection

These are more serious than an input the parser doesn't recognize, because each one returned needs_review: false — nothing would have signaled that the result was wrong.

Causes: the leading-number regex used a word boundary (\b) after the digits, which never matches between a digit and a following letter — so "16oz" (no space) silently failed to parse at all, a gap a sloppily-written test had actually been hiding (see below). The same regex also didn't exclude a following %, so "2%" got torn into a number and a stray percent sign instead of staying one token. The word-quantity table only combined number *words* with "dozen" ("two dozen"), not a numeral with "dozen". Unit and container matching wasn't case-insensitive. And there was no concept of "this product is never sold as a bare count" — "1 milk" looked structurally identical to a legitimate "1 apple". Fixed each; all five are now regression tests.

A test that didn't test what it said it did

One existing test was written as "16oz yogurt".replace("oz", " oz") — apparently meant to normalize spacing in the fixture, it actually rewrote the input before parsing, so the unspaced form was never exercised. This is how the \b bug above went undetected by a test that looked, at a glance, like it covered exactly that case. Fixed to test both the spaced and unspaced forms as separate cases.

The missing dataset artifact

Parsing functions are necessary but were not, by themselves, the Checkpoint 2 deliverable — the plan calls for one reproducible normalized table. Added build_normalized_catalog.py, which produces normalized_catalog.csv (31,398 rows): explicit store_id/store_name/ snapshot_id/product_id columns (not implied by which file was loaded), raw title/category/size next to the parsed package-size fields, price_cents as an integer, parsing_status/parsing_reason, and explicit brand/variant columns that are empty for every row right now — present in the schema and not guessed, but not yet populated (deferred to Checkpoint 4, matching). Also added manual_review.py, which persists the required 20-products-per-store manual check (100 rows, seeded sample) to MANUAL_REVIEW.md instead of leaving it as console output from an earlier session. No discrepancies found in this pass.

Corrected corpus numbers

With DashMart's snapshot-mixing bug fixed, the real corpus is 31,398 rows (not 34,401): 28,276 resolved (90.1%), 1,830 missing size, 1,000 priced-by-weight, 222 unrecognized, 70 apparel/diaper size labels. Also worth stating plainly: 90.1% measures how much of the corpus produced *some* fixed size, not that the size is correct — that's a coverage number, not an accuracy number.

Checkpoint 2: package-size normalization and shopping-list parsing

2026-09-16 · normalizationparsingtesting

Two deterministic, vocabulary-based parsers, no ML: one turns a product's free-text package size (unit_size, e.g. "4.8 oz x 8 ct") into a fixed size or an explicit refusal; the other turns a shopping-list line (e.g. "a dozen large eggs") into a structured request or an explicit review flag. Full detail, including every failure mode found, is in dash/PARSING_AUDIT.md. This entry summarizes the results.

Dimensional analysis as the core rule

Both modules share one rule: weight, volume, and count are three independent dimensions, and a value in one is never converted into another. "12 oz" (weight) and "12 fl oz" (volume) are not the same kind of quantity, even though both write "12" and both write "oz." convert_amount() in normalize.py raises a ValueError if asked to convert across dimensions (e.g. pounds to fluid ounces); this is enforced in code and covered by a test, not just documented as a rule to follow.

Product normalization: results against real data

Ran parse_package_size() against the latest snapshot of all five stores (34,401 rows):

The "missing size" and "priced by weight" rows are not parsing failures — they are correctly identified cases where no fixed size exists to extract. The project plan specifically requires excluding priced-by-weight items (produce, deli, meat sold "by the pound") from automatic basket math in v1; this parser is what makes that exclusion possible to apply, rather than something to separately build.

Two patterns were added after inspecting the "unrecognized format" cases directly: bare "each"/"ea" (90 occurrences) is now read as a fixed count of 1, and the "3 pk x 56 ct" form (pack-of-packs with no weight/volume unit, ~38 occurrences) is now parsed as a count multipack, distinct from the already-handled "4.8 oz x 8 ct" form. A third change added a specific reason for apparel/diaper size labels ("Large", "Size 6-10") that were leaking into the unit_size field from unrelated listings — this didn't reduce the unresolved count, it made the reason for 74 of those rows specific instead of generic.

Shopping-list parsing: 50 targeted cases

Verified against the project plan's own four worked examples ("a dozen large eggs", "1 gallon whole milk", "2 bags of chips", "organic strawberries, 1 lb") plus 46 additional cases covering decimals, fractions, bare counts, abbreviated units, vague quantities ("some", "a few"), and ambiguous containers ("a box of", "a can of"). All 50 pass. Missing quantities, vague quantities, and ambiguous container units all produce needs_review: true with a specific reason, never a guessed number.

One real bug came out of writing the tests, not from inspecting code by eye: "two dozen eggs" initially parsed as quantity 2, product type "dozen eggs". The word-quantity table had "a dozen" and "one dozen" as literal phrases, so "two" matched alone as 2 and left the word "dozen" stuck in the leftover text instead of combining with it. Fixed by generating every "<number word> dozen" combination programmatically instead of hand-listing a couple of them, and added a test that checks for 24 specifically (not just "a number came out") so this class of bug would fail loudly again if reintroduced.

Deliberate limitations, recorded rather than patched

  • Bare "oz" is always read as weight, never volume, even for a liquid ("8 oz milk" resolves as weight-ounces). The plan requires keeping ounces and fluid ounces distinct; this enforces that literally instead of guessing intent from the product name. A real gap for natural phrasing, written down rather than silently special-cased for specific product names.
  • product_type is leftover text after quantity/unit/ modifiers are removed, not a canonical grocery taxonomy. Matching it against actual catalog products is Checkpoint 4's job.
  • pandas was not introduced in this checkpoint. Neither module needed a join or a groupby; both work directly on plain dicts from csv.DictReader. The project plan calls for pandas at the "data preparation" stage generally, but adding it here would have been a dependency with no operation that justified it.

Diagnosing and fixing scraper reliability on Sprouts

2026-09-16 · scrapingreliabilityconcurrency

The initial Sprouts crawl failed 115 of 325 pages (35%) on the first pass, versus 56–64 out of 200–325 for the other three stores. All failures recovered on the existing retry pass, so the data itself was fine, but the failure rate was high enough to check rather than assume an explanation. This entry covers what the check found, two bugs it surfaced in the scraper's own retry logic, and what changed as a result.

Two competing hypotheses

A higher failure rate on one store could mean the requests to it were getting rate-limited more (a server-side, load-dependent cause) or that its pages were slower/heavier to render (a per-page, content-dependent cause). Distinguishing these requires knowing, per failed request: the HTTP status code, whether it was an exception (timeout, connection error) or an HTTP response, and how long the request took before failing. The scraper wasn't recording any of that — a failed page was tracked as a bare (url, status) tuple, and only for pages that were still failing after the retry pass, so pages that failed once and then recovered left no record at all.

Adding the missing instrumentation

Changed fetch() to return a log dict per request with status, exception type, elapsed time, and response size for every attempt, and changed the retry accounting to write this out to <output>.failed_pages.json regardless of whether the retry pass later fixed the page. Also added: a shared Pacer class to space out request dispatch across worker threads and put every worker on hold when any one of them hits a 429 (previously each worker retried independently, so several could be mid-backoff and still firing into the same rate limit), exponential backoff with random jitter in place of a fixed linear delay, and honoring a server-supplied Retry-After header when present.

What the logs showed

Re-running Sprouts with this instrumentation in place:

RunFirst-pass failuresRecovered on retryItems
Original (no pacing, concurrency 6)115 / 3251156,770
With pacing, concurrency 636 / 325366,775–6,798
With pacing, concurrency 320–22 / 325all6,770–6,788

Across every run, and across every attempt within every failure (up to 5 retries per page), the status was HTTP 429, with no exceptions, no 5xx responses, and elapsed times under 1.6 seconds. That rules out slow/heavy pages as a cause (a timeout would show as a long elapsed time before failing; a 429 arrives quickly with a small response body, consistent with a rate-limit rejection, not a slow render). The result: rate limiting, not page weight, and it scales with request concurrency — each reduction in concurrency produced fewer first-pass 429s.

A bug in the fix itself

A code review caught a race condition in the pacing logic before drawing further conclusions from the concurrency comparison above. Pacer.wait() computed a worker's next allowed dispatch time under a lock, released the lock, and then slept until that time. If another worker's 429 extended the shared cooldown during that sleep, the first worker had no way to find out — it would wake up and dispatch at its original, now-stale time, inside a cooldown window meant to pause every worker. This meant the concurrency-3 numbers above were measured against a pacer that didn't fully enforce its own cooldown.

Fix: after waking from the sleep, re-check whether the cooldown deadline has moved past the current time; if so, recompute and wait again. Verified with a standalone test: a cooldown triggered from a separate thread while ten workers were mid-wait(), confirming every dispatch that occurred after the cooldown was armed landed at or after its deadline (a single dispatch that had already fired before the cooldown existed is expected and correct — a request already in flight can't be recalled).

Re-running Sprouts at concurrency 3 with the fix in place: 22 first-pass failures (in the same 20–22 range as before the fix), all HTTP 429 across all attempts, all recovered on retry, 6,770 items. But the run took about 1,129 seconds — noticeably longer than the same setting had taken with the race present. The earlier, buggy version was faster because it wasn't actually waiting out every cooldown it triggered; the fix trades that speed for the pacer's cooldown guarantee actually holding.

What's still open

  • Item counts varied slightly run to run (6,770–6,798, about 0.3%) even with the same settings. Plausibly timing-dependent (a category's contents changing between requests, or a marginal page landing on one side of a batch boundary), but this hasn't been checked by diffing the actual product IDs between runs, so it stays a hypothesis rather than a finding.
  • A page that returns HTTP success with zero parsed items is now counted and reported separately (pages_with_zero_items in the run summary), but the scraper still can't distinguish a genuinely empty sub-category from an unnoticed parser mismatch. None occurred in the runs above.
  • These are five sequential runs on a live, shared service, not a controlled experiment — DoorDash's own load and rate-limit state at the time of each run aren't known or held constant.

Decision: keep concurrency 3 as the working default for stores that show this level of rate-limit sensitivity. Every run now writes a .summary.json (settings, duration, pass/fail counts) and a .failed_pages.json (full per-attempt detail) next to its CSV, so this kind of question can be answered from saved data on future runs instead of requiring a fresh diagnostic pass.

Checkpoint 1: A reliable five-store catalog dataset

2026-09-16 · scrapingdata collection

DashCartCompare's whole premise is comparing a shopping basket across stores, which means step zero is: can we actually get a trustworthy catalog snapshot from five different stores on DoorDash? Today was about answering that, honestly, before writing a single line of matching logic.

Starting point

The repo already had a working scraper (dash/doordash_dashmart_scraper.py), but "already had" undersells it — nothing about talking to DoorDash was handed to us. It was built, store by store of reverse-engineering, against DashMart specifically: finding that DoorDash server-renders its data as Next.js "flight" payloads embedded in the HTML (no public API, no docs), discovering that category pages silently under-render relative to their reported item counts, and working out that decomposing a category into its sub-category chip pages recovers most of what a single page's batch limit hides. None of that came from a library or a tutorial; it's documented step by step in dash/doordash_scrape_findings.md because it took real trial and error to find. That effort was proven out against DashMart back in August (3,152 items). The open question for today: does the technique generalize to genuinely different storefronts — ALDI, Ralphs, Vons, Sprouts — or was it quietly tuned to DashMart's specific page shape without us realizing it?

Confirming we had the right stores

Before any full crawl, a validation spike sampled ten products each from every store DoorDash surfaces for ZIP 92117 (131 listings total — groceries mixed in with liquor stores, delis, convenience stores, etc). This mattered because DoorDash lists multiple storefronts per retailer: "Vons", "Vons Essentials", and "Vons Beer, Wine & Spirits" are three separate store IDs with three separate catalogs. Picking the wrong one would mean silently comparing against the wrong slice of a store's actual inventory.

Fundamentals aside — why store ID + product ID, not just product ID: look closely at those item IDs above: 1000042024938105 (16 digits) vs. 22646268230 (11 digits) vs. 43865789331 (11 digits), all from the same store. Different ID formats within one store isn't a bug — DoorDash's catalog blends items from different backend systems (DoorDash-native SKUs vs. pass-through IDs from the retailer's own inventory system). Product IDs can't be trusted to mean anything consistent even within a single source, let alone across five different ones. That's exactly why the data model uses (store ID, product ID) as the compound key, and never assumes two stores' IDs identify the same product.

What's not resolved yet

Sprouts failed 115 of its 325 pages on the first pass — noticeably worse than the 56–64 seen on the other three stores — though the retry pass fully recovered it, same as everywhere else. Right now that detail only exists in scrollback console output; it isn't captured anywhere the next person (future me) could see it without re-running the crawl. The plan's own pass criteria are explicit about this: partial coverage needs to stay visible, not get smoothed over into a single "it worked" item count. So the next piece of Checkpoint 1 is a proper coverage report — products, categories, missing fields, and crawl failures, per store — built from these five snapshots, not just relying on console logs from the run that produced them.
